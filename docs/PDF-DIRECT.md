# PDF 안의 이미지를 직접 갈아 끼우기 — 실험 기록

Figma 에 같은 문서를 두 번 내보내 달라고 하는 대신, 한 번 내보낸 PDF 안의 이미지 객체만
바꿔 끼울 수 있는지 본다. 되면 목표 용량 모드의 두 번째 패스(실측 26초)가 통째로 사라지고,
Figma 가 내보낼 때 우리 JPEG 을 품질 76 으로 다시 압축하는 것도 피할 수 있다.

**이 문서는 실험 기록이다. 여기 적힌 범위 밖은 아직 된다고 말하지 않는다.**

## 1차 — PDF 이미지 직접 교체 가능 (2026-09-12)

한 장짜리로 한정해 "객체를 정확히 찾아 바꿔 끼우면 자리와 색이 유지되는가, 파일 크기가
실제로 움직이는가" 만 확인했다. 대상은 3.2.0 으로 내보낸 31쪽 PDF 의 18쪽에 놓인 사진이다.

**대상 식별.** 치수로 고르지 않았다. 18쪽의 내용 스트림을 훑어 `q`/`Q`/`cm` 상태를 따라가며
`/이름 Do` 로 그려지는 것을 찾고, 그 이름을 쪽의 자원 사전에서 객체 번호로 바꿨다
(`tools` 밖 실험 스크립트 `pdffind.mjs`). 그 객체의 `SMask` 를 풀어 값이 전부 255 인 것을
확인해 불투명 사진임을 검증했다(`pdfmask.mjs`). 1514×725 · DCTDecode · 137,091 B.

**교체.** 그 JPEG 만 757×362 로 줄여 다시 끼웠다(`pdfswap.mjs`). 배치 행렬·색 공간·알파
마스크는 건드리지 않았다. PDF 는 이미지를 단위 사각형에 놓고 행렬로 늘이므로 해상도가
바뀌어도 자리는 그대로다 — 이번 실측이 그것을 확인한다.

| 확인 | 결과 |
|---|---|
| 위치 | 바뀐 화소의 상자가 배치 행렬로 계산한 자리와 일치. 그 바깥은 최대 차 3, 문턱(8) 넘는 화소 0개 |
| 색 | 평균 RGB 114.1·101.0·90.3 → 113.8·100.2·90.1 |
| 선명도 | 인접 화소 차 지표 6.525 → 5.293 (해상도를 절반으로 줄인 결과와 맞음) |
| 텍스트 | `pdftotext` 결과 동일 |
| 파일 크기 | 9,778,721 → 9,702,796 B. 차이 75,925 B 가 JPEG 차이 75,929 B 와 일치 |

크기에는 대조군을 뒀다. 같은 도구로 **원본 JPEG 을 그대로 다시 끼워** 저장하면 9,778,721 B
로 원본과 같다. 도구 자체가 크기를 바꾸지 않는다는 뜻이고, 줄어든 몫은 전부 이미지에서 왔다.

**결론: Figma 에 다시 내보내 달라고 하지 않고 PDF 안의 사진을 바꿔 파일 크기를 조절할 수 있다.**

**아직 말하지 않는 것.** 보이는 창이 바뀌는 잘라 넣기, 투명 영역이 있는 이미지, 폼 안에
중첩된 이미지, 같은 이미지를 여러 쪽이 공유하는 경우는 손대지 않았다. 일반 문서 지원
여부와 시간 절감 폭도 아직 확정하지 않는다.

**한계 하나.** 이번에는 Figma 가 이미 품질 76 으로 재압축한 JPEG 을 다시 줄였으므로 화질이
두 번 깎였다. 실제 구현은 우리가 들고 있는 원본에서 바로 만들어 넣는다 — 2차에서 본다.
