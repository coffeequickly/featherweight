# 이미지 후보 재사용 — Figma 실기 검증

2026-09-12. 대상 변경: `codex/image-reuse-verified`. 기준은 `163f66d` 소스(제품 코드 3.2.0), 신규는 후보 이미지 캐시와 메모리 추정에 따른 작업 큐를 추가한 빌드다. PDF 직접 처리 및 별도 `perf/reuse`의 텍스트 재사용은 포함하지 않는다.

## 결론

이 표본에서는 출력 내용을 유지하며 목표 용량 내보내기가 평균 약 5% 빨라졌다. 균형 모드, 이미지가 많은 추가 표본, 취소 후 즉시 재실행에서 회귀를 발견하지 못했다. 앱 전체 메모리 감소나 임의의 대형 문서 안전성을 입증한 것은 아니다. Figma의 두 번째 내보내기를 없애는 변경도 아니다.

## 조건과 시간

같은 Figma 데스크톱 문서에서 **동일한 dev 플러그인 ID**의 빌드 파일만 교체했다. 저장 폰트와 설정이 다른 두 플러그인을 비교하지 않았다. 소스 문서를 편집하지 않고 선택만 바꿨다. 시간은 결과 화면 표시값이며 저장 대화상자 조작 시간을 더하지 않았다. 측정 중 PDF 렌더 분석은 실행하지 않았다.

- 31쪽: `피그마 테스트` 페이지의 `포트폴리오` 섹션. 1920×1080, 이미지 54종, 텍스트 446개 중 439개 폰트/7개 아웃라인.
- 목표 용량: 10MiB(10,485,760 B). 모든 실행이 배율 1.75×·최대 2560px·JPEG 92%를 선택했다.
- 잘라 넣기·하이퍼링크·글리프 폴백 켬, 모든 텍스트 아웃라인 끔. 균형 비교도 양쪽 설정 동일.
- 목표 용량 3쌍은 기준/신규를 교대로 실행. 균형·추가 표본은 각각 한 쌍이다. 재실행은 취소한 플러그인을 닫지 않고 시작했다.

| 대상 | 기준(초) | 신규(초) | 비고 |
| --- | ---: | ---: | --- |
| 목표 10MiB, 1회 | 87.0 | 81.2 | 같은 후보 선택 |
| 목표 10MiB, 2회 | 84.2 | 80.9 | 같은 후보 선택 |
| 목표 10MiB, 3회 | 87.5 | 83.7 | 같은 후보 선택 |
| **목표 용량 평균** | **86.23** | **81.93** | **4.30초, 4.99% 단축** |
| 균형, 31쪽 | 39.2 | 38.3 | 단일 비교, 통계적 개선 주장 안 함 |
| 균형, 취소 후 재실행 | — | 38.2 | 정상 저장 |
| 이미지 많은 3쪽, 목표 10MiB | 35.8 | 33.0 | 단일 비교 |

추가 표본은 `(구)이력서`의 `9`·`이미지`·`메리츠화재 - 3` 세 프레임이다. 이미지 paint 51개, 플러그인 집계는 고유 이미지 41종이다. 5691×8837의 큰 이미지 보드 한 쪽과 1920×1080 두 쪽을 포함한다. 두 빌드 모두 배율 2×·최대 4096px·JPEG 98%·PNG 유지가 선택됐고, 텍스트 9개 중 같은 Nexa Heavy 1개가 아웃라인이었다. 이것을 이전의 89쪽 표본이라고 부르지 않는다.

## 출력 동등성

저장한 PDF 11개를 비교했다. 각 실행을 같은 모드의 기준 PDF와 비교한 이미지 스트림(알파 마스크 포함)의 압축 바이트·치수·자원 경로, 추출 텍스트, 폰트 목록, 페이지 크기, 해제한 페이지 콘텐츠 스트림, 링크 액션이 모두 같았다. 폰트 파일 자체의 스트림 동등성을 별도로 검사한 것은 아니다.

- 목표 용량 31쪽: PDF 약 9,778,718 B. 이미지 66개 + 마스크 66개, 폰트 목록 20종 일치.
- 균형 31쪽: 약 7,888,648 B. 취소 후 재실행 결과도 같은 구조와 내용.
- 추가 3쪽: 양쪽 5,790,440 B. 이미지/마스크 스트림 96개, 폰트 목록 4종 일치.
- 목표 용량 첫 쌍 **31쪽 전부**, 균형 쌍 **31쪽 전부**를 Poppler 144dpi RGB로 렌더: 최대 채널 차이 **0**.
- 추가 표본 **3쪽 전부**도 렌더 차이 0. 보통 크기 두 쪽은 144dpi, 큰 보드 한 쪽은 메모리를 제한하려고 **35dpi**로 비교했다.
- 대표 사진 페이지를 이미지로 열어 배치·텍스트·사진도 확인했다. 2·3회 목표 출력과 취소 후 재실행은 구조/스트림을 비교했으며 별도 전체 렌더는 반복하지 않았다.

파일 전체는 실행별 메타데이터 등을 포함하므로 수 바이트 다르다. PDF 파일 전체가 바이트 동일하다는 주장은 하지 않는다. 수치와 페이지별 렌더 결과: [IMAGE-REUSE-FIGMA.json](IMAGE-REUSE-FIGMA.json).

## 취소와 상태 복구

신규 균형 내보내기 **18/31쪽 진행 중** 실제 취소 버튼을 눌렀다. 클릭 후 취소 토스트·내보내기 버튼 복귀 확인까지 약 **0.732초**였다. 내보내기 시작 후 6초에 취소했다고 기록하지 않는다. 취소 구간에 생성된 PDF나 저장 대화상자는 없었다. 같은 플러그인에서 곧바로 재실행해 38.2초에 정상 저장했고, 기존 균형 PDF와 내용이 같았다.

마지막에 Figma API로 두 검증 페이지의 `__sheaf_tmp__` 잔여 클론이 모두 0임을 확인했다. 개발 빌드와 검사 도구를 복구하고 현재 페이지/선택을 `피그마 테스트`의 `사진 카드` 컴포넌트로, 설정을 목표 10MiB·잘라 넣기 켬으로 돌렸다.

## 메모리 — 관측과 한계

Figma 앱과 Helper 프로세스 RSS 합계를 0.5초 간격으로 측정했다. 아래는 MiB, 시작/최고점이다. 실행 구간에는 일부 UI 준비·저장 처리가 포함된다.

관측 중 메모리 부족 종료는 없었다. 반복 실행 후 사용량이 내려오는 구간도 있었다. 하지만 시작점이 다르고 앱 전체 RSS에는 다른 문서·공유 메모리·브라우저/GPU 처리가 섞인다. **메모리가 줄었다거나 늘지 않는다고 결론 내리지 않는다.** 플러그인만의 할당량, 단일 초대형 이미지, 장시간 누수, 89쪽 문서는 아직 검증하지 않았다.

구현의 200MiB 캐시 상한과 192MiB 작업 추정 예산은 이 RSS의 상한이 아니다. 한 장이 예산을 초과하면 단독 처리하므로 그 한 장의 절대 메모리 한도도 보장하지 않는다.

## 커밋 대상 검사

다른 PDF 직접 처리 실험의 미커밋 파일을 제외하고, Git 인덱스의 파일만 별도 디렉터리에 꺼내 검사했다. **62개 파일, 703개 테스트 통과, 644개 건너뜀**. 타입 검사·ESLint·Prettier·빌드도 통과했다. 앞선 작업 트리 전체의 712개에는 이번 커밋에 포함하지 않는 PDF 실험 테스트 9개가 섞여 있었다.

## 재현 자료와 남은 범위

- 입력/출력 PDF는 개인 자산이라 커밋하지 않는다. 이 컴퓨터 Downloads의 `fw-reuse-*.pdf`에 있다.
- 로컬 원시 측정·비교 스크립트와 JSON은 git 제외 경로 `samples/image-reuse-20260912/`에 보관한다. `compare.py A.pdf B.pdf output-directory`는 Python의 pypdf/Pillow와 Poppler를 사용한다.
- 커밋에는 구현·단위 테스트·브라우저 비교 도구·집계 보고서만 포함한다.
- PDF 직접 교체, WASM 인코더, 준비 대기 변경은 이번 검증 범위 밖이다. 더 큰 속도 개선은 별도 설계/검증이 필요하다.
