# 보이는 창만 잘라 넣기 — 설계 (3.2)

> 검증 기록은 [IMAGE-CROP-VALIDATION.md](IMAGE-CROP-VALIDATION.md).

## 한 줄

Figma 는 잘라 쓴(CROP · 비율이 어긋난 FILL) 이미지를 PDF 에 **통째로** 싣고 클립한다 —
5% 창에도 4000×4000 이 들어간다. 그 자리에 보이는 창만 잘라 넣되, **자리마다 기존 출력의
픽셀 밀도를 밑돌지 않고, 실제 바이트가 줄 때만** 한다.

## 우선순위

위치·모양 보존 → 선명도 유지(같은 설정의 기존 출력이 바닥) → 용량 → 처리 시간.
품질을 내려 얻는 절감은 성과로 치지 않는다. 픽셀이 늘어도 "화질 개선" 이라 적지 않는다.

## 흐름 — export 와 목표 용량 예측이 같은 것을 본다

```
자리 수집 (main/images.ts collectImageUsages)
  → 계획 (lib/imageCrop.ts frameImagePlan = planImageTargets + planCrops)
  → 인코딩 (UI: W₀ 는 resize.ts, 조각은 resizeMany / probe 는 imageCache.ts 가 한 번 디코드)
  → 채택 (lib/imageCrop.ts chooseCrop — export 의 cropOne 과 예측의 tallyProbe 가 같이 쓴다)
```

- **창**(`lib/cropWindow.ts`): CROP 은 `imageTransform`(노드 단위좌표 → 원본 단위좌표, 실측 확인)이
  보여 주는 창 — 자르기 모드에서 이미지를 돌리거나 뒤집은 것도 창이 기울어질 뿐이라 잘라 넣는다.
  FILL 은 노드 로컬 상자로 가운데 창, 채우기 회전(90° 단위)은 돌린 이미지 위에서 가운데를 잡아
  원본 좌표로 되돌린다(90 = 시계 방향, 실측 R2). 원본 밖으로 나간 창·FIT·TILE 은 창이 없다 →
  기존 경로. 가장자리를 조금 넘는 것은 안으로 들인다(허용 오차 2e-3) — float32 부스러기만이 아니라, Figma 의 자르기 도구로 가장자리까지 끌어 놓은 창은 실측 5.6e-5 ~ 3.4e-4 만큼 원본 밖으로 나가 있었다(2026-09-11, 포트폴리오 4-1). 넘친 부분은 원본에도 조각에도 그릴 것이 없어 결과가 같다.
- **조각**: 창(기울어졌으면 그것을 감싸는 축 정렬 사각형)을 담는 정수 사각형 + 1px 여유. 꽂을 변환
  T′ = C ∘ T — T 에 회전이 있어도 그대로(단위좌표라 조각을 몇 배로 줄이든 그대로). 사각형이 같은
  자리끼리 조각을 나눠 쓴다. 실측(2026-09-11): 노드 15° 회전·가로 뒤집기·자르기 모드 20° 회전·
  FILL 90° 네 경우 모두 기존 대비 어긋남 ≤ 0.04 pt, 윤곽 불일치 ≤ 0.01%.
- **밀도 바닥**: 기존은 해시마다 전체본 하나(W₀, 목표 T₀)를 모든 자리가 나눠 쓴다. 조각 목표는
  여백·양축 반올림까지 넣어 W₀ 의 원본 픽셀당 밀도를 양축 다 만족하는 최소값(이분 탐색), 그리고
  제 목표(놓인 크기 × 배율, 최소·최대 안) 이상. 조각 변은 정수라 반 픽셀 못 미치는 것은 반올림으로
  본다(안 봐주면 목표가 최대치에 걸린 자리가 641 vs 641.28 로 탈락한다). 못 맞추면 기존 경로.
- **통째로 보는 자리가 하나라도 있으면 그 원본은 기존 경로** — W₀ 가 남아야 하니 조각은 순수
  추가다. 같은 원본을 쪽마다 다르게 쓰면 결정도 쪽마다(PDF 는 쪽마다 한 벌씩 싣는다).
- **채택**(`CROP_RULES`, 한곳): 밀도가 기존과 거의 같은 후보는 5% 이상 줄어야, 밀도 이득이 1.5배
  이상인 후보는 따로 두고 1% 만 줄어도 채택. 조각이 12개를 넘거나 조각 픽셀 합이 W₀ 를 넘으면
  인코딩 전에 기존 경로. 값은 실측으로 조정한다.
- **복구**: 조각 인코딩·생성·되읽기가 실패하면 이미 만든 W₀ 를 꽂고 `recovered` 로 센다 —
  출력은 정상이라 경고가 아니라 안내("기존 방식으로 최적화했습니다"). 취소면 복구하지 않고
  바로 나간다. 예측(tallyProbe)도 같은 규칙.
- **캐시**: W₀ 는 `해시|목표|품질|PNG설정`, 조각은 `해시|사각형|목표|품질|PNG설정` — 다음 쪽이
  같은 것을 쓰면 UI 왕복도 createImage 도 없다.

## 건드리지 않은 것

- 준비 대기 `settleDelayMs(꽂은 장수)` — 조각 수만큼 늘어난다(장당 300ms, 상한 4s). 줄이는
  일은 별도: 정상 이미지가 실렸는지 확인하는 방법과 오판·시간 초과 복구를 검증한 뒤.
- 부모 클립으로 잘리는 부분은 자르지 않는다(개선 계획 37).
- 스트로크의 이미지 paint, 보이지 않는 fill 은 예전처럼 손대지 않는다.

## 실측 (2026-09-10 · 사진 3000×4000 · 균형)

- 자리 넷(창 10·25·5%·FILL 가로띠) 묶음: 573K → 302K(−47%), 자리마다 픽셀 ≥ 기존, 위치 ≤ 0.04pt.
- 전체가 보이는 자리를 하나 더 넣으면 +323K → 기존 유지.
- 포트폴리오 31쪽: 20.30MB → 19.78MB(−2.55%), 11곳. 대부분이 전체가 보이는 자리와 원본을
  나눠 써서 규칙대로 기존 유지 — 품질을 지킨 채 얻는 이득의 정직한 크기.

## EXIF 방향 (2026-09-11 실측으로 고침)

세로로 찍어 EXIF 태그로 돌린 JPEG(방향 5~8)는 SOF 의 원시 크기(가로)와 Figma 가 보여 주는 크기(세로)가
다르다. 긴 변만 쓰던 통째 축소에서는 상관없었지만 창은 축마다 좌표가 필요해서, 시나리오 S15 에서 조각이
엉뚱한 자리에서 잘렸다(기존 대비 40 이상 차이 픽셀 8.6%). 지금은 `imageHeader` 가 APP1 의 방향 태그를
읽어 5~8 이면 가로세로를 바꿔 돌려주고, UI 의 디코드(`createImageBitmap`)도 방향 적용을 명시한다 — 두
좌표계가 같다. 크기 캐시 키를 `imageSizes2` 로 바꿔 예전에 읽어 둔 값은 한 번 다시 읽는다. 고친 뒤 S15 의
차이는 0.06% 로 내려갔다(JPEG 재인코딩 차이만).

## 검토 반영 (2026-09-11, 29a079a 검토)

- **목표 용량 탐색.** 기준이 목표를 넘으면 더 센 칸만 보던 전제는 잘라 넣기와 맞지 않는다. 조각 채택은 계획이
  아니라 인코딩 뒤 절감률로 정해져 칸마다 다르다 — 같은 계획이라도 기준은 절감 3% 로 전체본(1,000KB), 한 칸
  위는 18% 로 조각(980KB)일 수 있어 더 선명한데 더 작다(2차 검토 재현). "기준에 없던 조각 계획이 붙는 칸만"
  으로 거르는 첫 수정은 이 경우를 놓쳐서 걷어냈다. 지금은 잘라 넣기가 켜져 있으면 더 선명한 칸도 품질 순으로
  전부 재보고 목표에 드는 첫 칸에서 멈춘다(`probeOrder`). 값은 후보 설정 평가 최대 세 번 추가 — 평가마다
  문서의 이미지와 조각을 전부 인코딩하므로 큰 문서는 시간이 꽤 늘 수 있다.
- **EXIF 위치.** APP1 이 SOF 뒤, SOS 앞에 오는 파일이 있다. 크기를 들고 SOS 직전까지 메타데이터를 마저 본다.
  방향 태그는 SHORT 하나일 때만 믿는다.
- **조각 실패 집계.** UI 가 정상 회신으로 실패를 알린 것도 예외와 같은 복구다 — 예전엔 "절감 부족" 과 섞여
  복구 0 으로 셌다. 이제 채택/절감 부족/실패를 갈라 돌려주고 실패만 센다.
- **FILL 각도.** 90° 배수에서 1e-3° 안쪽만 받는다. 90.4° 는 반올림하지 않고 기존 경로(통째).
- 밀도 바닥은 "양축 저장 픽셀이 기존 이상" 이되 정수 반올림으로 생기는 반 픽셀은 봐준다 — 엄밀한 "항상 이상" 이
  아니라 "반 픽셀 안에서 이상" 이다. 조각 픽셀 합 관문은 인코딩 비용을 줄이는 추정이지 바이트 판정이 아니다.

## 목표 용량 모드 실측 (2026-09-11 밤, 2b32618 이후 빌드, 포트폴리오 31쪽·이미지 54장)

목표 5 MB(앱 기준 5,242,880 B)는 기준 칸(≈7.9 MB)보다 낮아 새 탐색 순서를 탄다. 잘라 넣기 켬 4,944,716 B
(92.0 s, 후보 평가 9단계) vs 끔 5,169,470 B(85.2 s, 6단계) — 켬이 4.35% 작다. 둘 다 PDF 의 이미지 긴 변은
1280px 칸이지만 마지막 단계가 품질 변형을 재보므로 최종 품질까지 같다고는 못 한다 — PDF 로는 확인 불가(Figma 가
내보낼 때 다시 인코딩해 네 PDF 의 JPEG 69장이 같은 양자화표·ICC 프로필). 그래서 결과 탭에 자동 선택 설정을 적고
후보별 예측치를 콘솔에 남긴다. 선명한 칸 셋은 조각을 써도 5 MB 에 못 들어 이 문서에선 추가 평가가 결과를 바꾸지
않았고, 총시간 차는 +6.8 s(후보 평가 3회 + 조각 생성·대기·실행 변동 포함, 단일 실행). 끔 결과는 십진 5,000,000 B
제한이라면 초과다. 목표 10 MB 는 기준이
목표 안이라 예전 경로(선명한 쪽만) — 9,033,771 B, 84.2 s, 기준 칸(2048·0.8). 기존 빌드는 그 플러그인 저장소에
폰트 파일이 없어 텍스트가 전부 아웃라인(고정분 12 MB)이라 비교군으로 못 썼다.

## Figma 재인코딩 확인 (2026-09-11 밤)

같은 사진(600×403)을 품질 60/80/95 로 인코딩해 나란히 놓고 균형(원본 유지)으로 내보냈다. 입력 28,260 /
41,653 / 88,112 B(서로 다른 DQT) → PDF 안 31,390 / 39,972 / 37,144 B, 셋 다 같은 양자화표·ICC 프로필. Figma 가
우리 JPEG 까지 다시 인코딩한다는 뜻이고, 품질 95 입력이 80 보다 작아지기도 한다. 따라서
- 이 표본에서 확인된 것은 셋이다: Figma 가 JPEG 를 재인코딩한다, 입력 JPEG 바이트로 최종 PDF 바이트를 그대로
  예측할 수 없다, 입력 품질과 최종 용량의 관계가 단조롭지 않다(같은 해상도에서도 31,390~39,972 B, 27% 차).
  "품질이 용량에 거의 영향 없다" 까지는 아니고, 입력에서 잃은 디테일은 되돌아오지 않으니 품질은 시각적
  결과에도 여전히 영향을 준다.
- `predictSize` 의 "우리 JPEG 는 그대로 실린다" 전제는 틀렸다. 예측이 과하면 필요 이상으로 압축한다. 예측식 수정은 기준·최종의 예측 대 실제 오차(결과 탭 "예측 ·, 실제 ·",
  콘솔 [fit])를 모은 뒤에 한다 — 보정비를 전체에 곱하는 단순 수정은 하지 않는다(실측: 예측 5.8MB → 실제 8.0MB).
- 크롭 자체와는 무관한 기존 전제다.
