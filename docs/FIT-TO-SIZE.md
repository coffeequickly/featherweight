# Fit to Size — PRD (v1)

> Status: in progress · 2026-08-27
> 원안 검토 후 §7·§8(탐색 알고리즘)을 예측 기반으로 교체한 버전.

## 한 줄

목표 용량을 입력하면, 그 아래로 들어가는 선에서 **가장 좋은 화질**을 골라 PDF를 만든다.
텍스트·폰트는 손대지 않는다.

## 왜 필요한가

사용자는 `quality 0.72`나 `maxEdge 1600`을 원하지 않는다. "5MB 아래로"를 원한다.
채용 사이트 5MB, 메일 첨부 10MB, 제출 시스템 3MB — 제약은 늘 용량으로 온다.

## 하지 않는 것

- 정확히 N MB 맞추기 (목표는 `≤ target`)
- 페이지 삭제·텍스트 래스터화로 목표 달성
- 최소 품질 아래로 자동 압축
- vector 단순화, PDF 구조 최적화, 폰트 추가 서브셋

## 핵심 설계 — 다시 export 하지 말고 예측한다

원안은 시도마다 PDF 전체를 다시 만들었다. 우리 파이프라인에서 export 1회는
clone → 이미지 왕복 → `settleDelayMs` 대기(최대 4초) → exportAsync → 머지다.
11쪽 문서 실측이 4.8초였고, 4회면 20초가 넘는다.

PDF 크기는 사실상 이렇게 나뉜다:

```
PDF 크기 = 고정분(텍스트·폰트·벡터·구조) + Σ이미지 바이트
```

그리고 **이미지 인코딩은 UI에서 Figma 없이** 할 수 있다(`resize.ts`, 캔버스 작업).
그래서 탐색은 Figma 왕복 0회로 끝난다.

```
1) 기준 export 1회 (Balanced)
   → 실제 PDF 크기와 Σ이미지 바이트를 동시에 얻는다
   → 고정분 = PDF 크기 − Σ이미지 바이트          ← 여기서 확정

2) 탐색 (UI 메모리, Figma 미개입)
   후보 프로필마다 캐시된 원본을 재인코딩해 Σ바이트만 잰다
   예측 = 고정분 + Σ새 이미지 바이트
   → 조건을 만족하는 것 중 최고 품질을 고른다 (탐색이 아니라 선택)

3) 선택한 프로필로 실제 export 1회
```

전체 export **2회**. 후보를 6~8개 재도 비용은 거의 안 는다.
부수 효과로 "예상 크기"가 사실상 공짜로 나온다.

### 왜 이진 탐색을 안 쓰는가

`keepsOriginal()`(재인코딩 결과가 더 크면 원본 유지) 때문에 압축을 세게 해도
크기가 그대로인 구간이 생긴다. 단조롭지 않은 계단 곡선이라 이진 탐색은 헛돈다.
후보를 전부 계산해두고 고르면 이 문제 자체가 사라진다.

## 하한 — 시나리오 C를 즉시 판정한다

어떤 설정에서도 줄지 않는 바이트가 있다:

| 규칙 | 효과 |
|---|---|
| `KEEP_BYTES_FLOOR` (100KB) | 원본이 이보다 작으면 무접촉 |
| `MIN_TARGET_LONG_EDGE` (640) | 그 아래로는 축소하지 않음 |
| `processFloor` (프레임 예산) | 프레임 크기 안에 드는 이미지는 무접촉 |
| `keepsOriginal()` | 재인코딩이 손해면 원본 유지 |

```
하한 = 고정분 + Σ(손 못 대는 이미지) + Σ(최소 품질에서의 나머지)
```

1회차 직후에 계산되므로, 불가능한 목표는 **시도 없이 바로** 알려준다:
"1 MB는 불가능합니다. 이 문서의 최소 크기는 2.4 MB입니다."

## 최소 품질 가드

목표를 맞추려고 무한정 낮추지 않는다. v1 하한:

```
quality   ≥ 0.60
multiplier ≥ 1.0
maxEdge   ≥ 1024
```

"몰래 품질을 망치지 않는다"는 기존 원칙의 연장이다. 못 맞추면 못 맞춘다고 말한다.

## 프로필

`Settings`의 `multiplier`/`maxEdge`는 UI 세그먼트와 묶인 union 타입이다.
탐색용 연속값을 그 타입에 밀어 넣지 않고, 별도 `CompressionProfile`을 쓴다.

```ts
type CompressionProfile = {
  multiplier: number
  maxEdge: number
  quality: number
  reencodeOpaquePng: boolean
}
```

사다리(좋음 → 작음)를 미리 정의하고 그중에서 고른다.

## UI

메인 화면 맨 위 프리셋의 네 번째 칸이 `목표 용량` 이다. 고르면 배율·상한·품질은
사다리가 정하므로 값 칩은 `자동` 하나만 남고, 고급 설정에서는 크기·압축 섹션이
안내 문장으로 바뀐다 (2.0).

```
[선명하게][균형][최소 용량][목표 용량]
파일 크기  [ 5 ] MB 이하
[▣ 자동]
```

- 입력: 0.5 ~ 500 MB, 소수점 1자리, 기본 5.0
- 체크리스트 이미지 줄: `이미지 10장 · 화질은 5.0MB에 맞춰 정합니다`
- 진행 표시는 기존 단일 축에 녹인다 (시도마다 0% 로 되돌아가지 않는다)

## 결과 리포트

```
달성:      22.7MB → 4.8MB · 목표 5.0MB 달성
이미 작음:  3.2MB · 추가 압축이 필요 없었습니다
불가능:    2.4MB · 목표 1.0MB 는 화질을 크게 해쳐야 가능합니다
```

## 캐시

원본 이미지를 UI 세션 동안 해시로 캐시한다(재전송 방지). 총량 상한을 두고
넘으면 오래된 것부터 버린다. export 종료 시 즉시 비운다.

## 수용 기준

- **AC1** 22.7MB 문서에 목표 10MB → 결과 ≤ 10MB
- **AC2** 목표를 만족하는 후보 중 가장 높은 품질을 고른다
- **AC3** 실제 export 는 최대 2회
- **AC4** 최소 품질 아래로 자동 압축하지 않는다
- **AC5** 이미 목표보다 작으면 추가 압축하지 않는다 — 대신 더 선명한 후보(사다리
  맨 위, 선명하게와 같은 자리까지) 중 목표 안에 드는 것이 있으면 그것을 쓴다.
  목표는 한도가 아니라 예산이다
- **AC6** Fit 전후로 텍스트 추출·폰트 임베드·fallback·페이지 순서가 동일하다
- **AC7** 취소·실패 후 `__sheaf_tmp__` 가 남지 않는다

## 단계

1. **Phase 1** — 프로필 사다리·선택 로직(순수 함수 + 테스트), 목표 입력 UI,
   probe 경로, 하한 판정, 결과 리포트
2. **Phase 2** — 이미지별 예산 배분(큰 것부터 깎기), 예상 크기 상시 표시
3. **Phase 3** — 시각 중요도 기반(히어로 이미지 보존)

## 메시지

알고리즘을 설명하지 않는다.

> Fit this PDF under 5 MB. → 22.7 MB → 4.8 MB. Target achieved.

## 구현 메모 (Phase 1)

지어 놓고 보니 PRD 와 달라진 부분, 그리고 왜 그렇게 됐는지.

### 크기는 UI 가 잰다

고정분을 구하려면 **머지가 끝난 PDF 의 실제 크기**가 필요하다. 폰트 서브셋 임베드는
UI 에서 일어나므로, 메인이 가진 부분 PDF 바이트를 다 더해도 실제 파일보다 작다 —
텍스트 위주 문서에서는 그 차이가 곧 파일 전체다.

그래서 기준 패스는 이렇게 끝난다:

```
main → 'done' { measureOnly: true, reqId }
UI   → 머지(폰트 포함) → 저장하지 않고 크기만 잰다
UI   → 'fit:measured' { reqId, pdfBytes, imageBytes }
```

UI 는 이때 부분과 머지 결과를 들고 있는다. 2회차가 아무것도 안 보내면 —
이미 목표 이하이거나, 잴 후보가 없었거나, 취소됐을 때 — 그걸 그대로 저장한다.
같은 문서를 두 번 뽑지 않는다.

머지가 실패하면 `pdfBytes: 0` 으로 알린다. 메인은 예측할 근거가 없다고 보고
탐색을 접은 뒤 기준 결과로 마무리한다 — 사용자는 파일을 받고, 목표 문구만 없다.

### 위쪽으로도 찾는다 (2.2)

처음에는 기준(균형)이 목표 안에 들면 거기서 끝냈다. 5MB 를 적었는데 1.8MB 가 나오면
예산 3MB 를 그냥 버리는 셈이다 — 채용 사이트 상한을 적는 사람은 그 안에서 가장 좋은
것을 원한다. 그래서 기준이 목표 안이면 후보를 반대쪽(더 선명한 쪽)으로 잡아, 좋은
것부터 재고 처음 목표 안에 드는 것을 고른다. 천장은 사다리 맨 위 = 선명하게 프리셋과
같은 자리다. 10MB 를 적었다고 0.4MB 이력서가 9MB 가 되지는 않는다 — 선명하게로
뽑았을 크기까지만 간다.

### Figma 가 다시 압축하는 몫을 보정한다 (2.2)

"PDF = 고정분 + Σ이미지 바이트" 는 우리가 넣은 바이트가 그대로 PDF 에 실린다고 가정한다.
실제로는 Figma 가 손대지 않은 원본(특히 PNG)을 자기 방식으로 다시 압축해 넣어서,
31장 덱에서 우리 셈이 PDF 전체보다 커 고정분이 0 으로 잘리고 압축을 세게 한 후보가
기준(9.5MB)보다 크게(27MB) 예측됐다. 결과는 가장 센 칸으로 떨어졌다. 기준 패스의 머지
결과에서 PDF 안의 실제 이미지 바이트(XObject 합)를 같이 재서, 고정분은 그것으로 구한다.

비율은 **우리가 만든 JPEG 에는 곱하지 않는다.** pdfimages 로 보면 우리 JPEG 는 PDF 에
그대로(DCT) 실리고, Figma 가 다시 넣는 건 손대지 않은 원본과 PNG 로 남긴 출력이다.
비율 하나를 전부에 곱했더니 우리 JPEG 가 많은 후보가 작게 예측돼 5.8MB 예측이 8.0MB 로
나왔다(목표 9.5 안이었지만 운이다). 그래서 바이트를 `{ total, jpeg }` 두 갈래로 세고,
비율 = (PDF 안 실제 − 우리 JPEG) / (우리 셈 − 우리 JPEG), 0.05~2 로 자른다.

### 칸 사이를 메운다 (2.2)

사다리 칸은 넓다. 특히 맨 위 칸만 PNG 를 그대로 두므로 스크린샷이 많은 덱은 한 칸
차이가 14MB 와 3.5MB 였다(31장 덱 실측). 9.5MB 를 적었는데 3.5MB 가 나오면 예산 6MB 를
버린 것. 그래서 맞는 칸을 찾은 뒤 그 칸 설정에서 JPEG 품질만 +0.08, +0.04(천장 0.98)
올린 변형을 선명한 것부터 재고, 목표 안에 드는 첫 것을 고른다. 최대 두 번 더 잰다.
품질 축만 움직이는 이유: 배율·상한은 어차피 대부분 이미지에 안 걸리고, PNG→JPEG 는
켜고 끄는 것이라 사이가 없다. 이미지별로 어떤 PNG 를 무손실로 남길지 고르는 건
Phase 2 의 일이다.

### 손대지 않은 이미지도 센다

`bytesBefore`/`bytesAfter` 는 **처리한** 이미지만 세고 있었다. 프레임 예산 이하라
건너뛴 로고, 100KB 이하라 그냥 통과시킨 이미지의 바이트가 빠져 있어서, 그대로 쓰면
고정분이 그만큼 부풀고 예측이 전부 어긋난다.

`bytesUntouched` 를 따로 세서 이미지 몫에 더한다. 리포트에 보이는
"이미지 N장 A→B" 는 그대로 둔다 — 손대지 않은 것까지 섞으면 그 문장이 거짓말이 된다.

### probe 항목이 원본 크기를 들고 다닌다

프로필이 세지면 기준선이 낮아지므로, 기준 패스에서 건너뛴 이미지가 후보에서는
처리 대상이 될 수 있다. 그래서 건너뛴 이미지의 원본도 `image:cache` 로 UI 에
넘겨 둔다 (Fit 일 때만).

그래도 캐시에 없는 경우를 대비해 `ImageProbeItem` 이 `originalBytes` 를 들고 간다.
캐시 미스면 원본 크기로 센다 — 예측이 실제보다 **크게** 나오는 쪽이라, 결과가
목표를 넘기는 것보다 안전하다.

### 진행률은 세 구간

export 를 두 번 하므로 0→100 을 두 번 반복하면 아무것도 못 읽는다.
한 축을 나눠 한 방향으로만 채운다: 기준 45% · 후보 재보기 15% · 최종 40%.

### 남은 것

- 후보를 좋은 쪽부터 재다가 목표를 만족하면 멈춘다. 사다리가 정렬돼 있어서
  그보다 센 후보는 화질만 더 버린다.
- 2회차 도중 취소하면 UI 는 1회차 결과를 저장한다. 파일은 온전하지만 화질이
  기준값이다 — "취소됨" 접두어는 붙는다.
- Phase 2(이미지별 예산 배분)는 손대지 않았다.
