# 후보 이미지 재사용과 메모리 기준 병렬 처리

2026-09-12, `codex/image-reuse-verified`. 이 변경은 PDF 직접 교체 실험과 독립적이다.

목표는 같은 설정의 출력 이미지 바이트를 유지하면서 중복 인코딩을 줄이는 것이다. JPEG 품질, 축소 알고리즘, 크롭 채택, Figma 준비 대기, 목표 용량 재시도 정책은 바꾸지 않았다.

## 구현

- 후보 평가에서 생성한 전체 축소본과 조각 바이트를 저장한다. 최종 패스는 동일한 원본 해시·목표 크기·품질·PNG 설정·크롭 사각형이면 그 바이트를 반환한다. 사각형의 네 값 모두 키에 포함한다.
- 메인에서 전체본과 조각 요청 모두 원본 해시를 전달한다. 원본 보관 여부는 별도 `keepOriginal` 필드다. 일반 내보내기에서는 탐색용 원본을 모으지 않는다.
- 결과 캐시는 LRU, 최대 64MiB/1,024항목이다. 원본 캐시가 먼저 공간을 차지하고, 두 캐시의 바이트 합계는 기존 200MiB 안에 둔다. 결과 캐시 때문에 예측용 원본이 추가로 밀려나지는 않는다. 캐시가 없으면 기존 인코더를 호출한다.
- 후보의 원본별 작업을 최대 네 개 겹친다. 원본 헤더 크기 × 16바이트 + 입력 바이트로 작업 메모리를 추정하고, 동시 작업의 추정 합계를 192MiB 이내로 제한한다. 크기를 모르거나 단독으로 예산을 초과하는 이미지는 혼자 실행한다. 전체본/조각의 일반 리사이즈도 같은 작업 큐를 이용한다.
- 종료·오류·취소·새 실행 시 캐시를 비우고 세대 번호를 갱신한다. 대기 작업은 취소하며, 이미 시작한 브라우저 작업은 끝나더라도 이전 실행의 바이트와 치수를 다시 기록하지 못한다. 진행 중 작업의 메모리 예약은 실제 종료 때 해제한다.

192MiB는 **작업 시작을 제한하는 추정 예산**이다. Figma 전체 RSS/GPU 메모리의 상한이나 단일 초대형 이미지의 절대 메모리 상한이 아니다. 메시지 전송, PDF 병합본, 브라우저 내부 복사본도 캐시의 200MiB에 포함되지 않는다.

## 검증

자동 회귀 테스트는 다음을 확인한다.

- 전체본·PNG 조각 재사용의 바이트와 메타데이터, 부분 캐시 적중 시 누락 조각만 인코딩하고 요청 순서 유지
- 원본·크기·품질·PNG 설정·사각형 변경 시 캐시 분리
- 캐시 부재·인코딩 실패 시 기존 반환 계약, 변경 없는 원본의 중복 보관 방지
- LRU 퇴출과 보관 바이트 계산, 원본/결과 캐시 공유 상한
- 작은 원본 네 개 병렬 처리와 동일한 페이지별 합계, 큰 작업 직렬화, 실패 후 예산 반환
- 취소된 대기 작업 미실행, 진행 중 작업의 늦은 완료로 인한 캐시/치수 오염 방지
- 메인 전체본/조각 요청의 해시 전달과 원본 보관 플래그 분리

실제 Chrome 152의 Canvas 인코더로 EXIF JPEG 사진과 합성 투명 PNG를 품질 74%, 80%에서 검사했다. 각 조건에서 전체본과 조각을 직접 인코딩한 뒤 후보 캐시 반환값과 세 번 비교했다. **24개 이미지 비교 모두 바이트·MIME·가로세로 일치**, 전체본의 `changed`도 일치했다. 정리 후 캐시 바이트는 0이었다.

측정한 구간은 전체본 1개 + 조각 1개의 인코딩/반환이다. 직접 인코딩 60.8~206.5ms, 캐시 반환 0~0.2ms. 0ms는 타이머 분해능 아래라는 의미다. 후보를 처음 만드는 비용, 브리지 복사, Figma `createImage`, 준비 대기, PDF 생성은 이 시간에 포함하지 않는다. **이 수치로 전체 내보내기 단축률을 주장하지 않는다.** 원시 기록: `IMAGE-REUSE-BROWSER.json`.

브라우저 검증을 반복하려면 별도로 설치된 Playwright와 Chrome을 지정한다. 프로덕션 의존성을 추가하지 않으며 사용자 브라우저 프로필을 사용하지 않는다.

```sh
PLAYWRIGHT_MODULE=/absolute/path/to/playwright-core/index.mjs \
CHROME_PATH=/absolute/path/to/chrome \
node tools/image-reuse-check.mjs /absolute/path/to/source.jpg /tmp/image-reuse-result.json
```

사진은 EXIF 적용 후 가로 1,420px 이상, 세로 1,700px 이상인 JPEG를 사용한다. 테스트는 고정 크롭 영역을 사용한다. PNG는 도구가 생성한다. 소스 사진은 저장소에 추가하지 않는다.

## 남은 실측과 범위

- Figma 실기 완료: 같은 31쪽·목표 10MiB에서 세 번씩 교대 실행한 평균은 86.2초 → 81.9초(약 5% 단축). 목표 용량/균형 출력의 31쪽 전체가 각각 144dpi에서 픽셀 동일했다. 메모리 감소는 입증하지 않았다. 조건·취소·추가 표본·제약은 [검증 기록](IMAGE-REUSE-VALIDATION.md), 수치는 [JSON](IMAGE-REUSE-FIGMA.json)에 있다. 다른 에이전트의 10% 개선 기록과 합산하지 않는다.
- 원본이 커서 메모리 예산을 넘으면 병렬 효과가 줄고, 캐시 공간이 부족하면 재인코딩한다. 성능보다 기존 출력 경로를 우선한다.
- `perf/reuse`의 텍스트 판정 재사용과 대기 실험 코드는 가져오지 않았다. PDF 직접 처리, WASM 인코더도 이번 변경에 포함하지 않는다.
