# PDF 직접 처리 2차 — 동일 해상도 교체와 무손실 재구성

2026-09-12 · `spike/pdf-direct` · 당시 제품 기능에 합치지 않은 실험.

이 기록에서 확인한 범위를 바탕으로 이후 보수적인 제품 fast path를 구현했다. 현재 설계,
fallback 조건과 31쪽 전체 문서 결과는 [EXPORT-PERFORMANCE.md](EXPORT-PERFORMANCE.md)를 본다.

## 판단

**직접 교체는 Figma iframe 안에서 실행됐다. 재인코딩을 한 번 없앤다고 화질과 용량이 동시에 좋아지는 것은 아니었다.** 같은 사진·같은 해상도에서 작은 후보는 일부 미세 무늬 지표가 낮았고, 원본에 더 가까운 후보는 파일이 커졌다.

별도로 JPEG의 저장 구조만 progressive로 바꾸면, **31쪽 표본에서 디코딩된 픽셀을 그대로 유지하면서 PDF가 1.96% 작아졌다.** 이 처리는 Mac의 네이티브 `jpegtran` 실험이다. Figma에 사용할 WASM은 아직 넣지 않았다.

## 1. 대상과 실험 조건

- 선택한 `사진 카드` 안 `카드 사진 CROP 30%`, 노드 `3759:88764`, fill 0.
- 원본 해시 `fdac1a36d6ff80c9dca17e8da5c7af600b88d412`, 3024×4032 JPEG, 2,796,292 B.
- 원본 SHA-256 `fae20c9ac6cc72da8bb788a34536bd49dcc15ea9a12554f0047d49545eb53c26`. 중단 전 복구한 JPEG와 일치한다.
- 이 paint만 380×200 임시 프레임에 재현했다. 원래 문서의 마스크·효과·주변 요소를 검증하는 실험은 아니다. 임시 프레임은 제거했다.
- 원본 크기 그대로 Figma를 거친 `reference.pdf`를 화질 비교 기준으로 삼았다. 이것도 Figma가 인코딩한 결과이므로 절대적인 원본 픽셀 기준은 아니다.
- 기존 경로 대조군은 제품의 `resizeImage`로 원본을 1440×1920, JPEG 80%로 만든 뒤 Figma에 넣어 내보낸 PDF다. **제품의 크롭 최적화를 켠 출력과 비교한 것은 아니다.** 재압축 단계의 차이만 분리했다.
- 직접 후보도 같은 원본을 같은 제품 함수로 1440×1920에 인코딩했다. JPEG 품질만 60/70/76/80/85/90/98%로 달리했다. 모두 원본 전체이고 크롭 변환은 그대로다.

## 2. 객체 연결과 보존 확인

이미지 크기로 대상을 검색하지 않았다. 사진 하나만 있는 캡처의 `/X1 Do`(27번 연산) → 페이지 자원 `/X1` → 객체 9를 연결했다. `bind.py`는 실제 콘텐츠 스트림을 파싱하여 paint에서 계산한 배치와 대조한다.

실제 CTM은 `[1266.666504, 0, 0, 1688.888916, -443.333282, -828.888916]`다. paint 계산과의 계수 차이는 최대 0.000113이다. 교체 전후 콘텐츠 스트림은 바이트까지 같다. JPEG 크기·불투명 알파 마스크·PDF 색 공간도 유지했다. PDF의 ICC는 sRGB2014이고 브라우저 JPEG의 ICC는 sRGB였다. 이 표본의 색 차이는 렌더로 확인했으며 임의의 색 프로파일 호환성을 보장하지 않는다.

`replace.ts`는 캡처 바이트, 이미지 스트림, 자원 참조, 치수, JPEG 형식, RGB 입력, 8비트 완전 불투명 마스크를 검사한다. 다른 페이지·추가 이미지 자원·다른 해상도·투명 마스크는 거절한다. **일반 문서에서 원본과 PDF 객체를 연결하는 기능은 아직 없다.**

## 3. 같은 해상도에서의 화질과 용량

216dpi Poppler 렌더, 1140×600. PSNR은 RGB, SSIM은 휘도·11×11 균일 윈도우의 진단값이다. 지표 하나로 화질 동등을 판정하지 않았다. 옷감·붉은 끈·팔 윤곽 확대도 비교했다.

| 경로 | PDF 바이트 | PSNR ↑ | SSIM ↑ | 판단 |
|---|---:|---:|---:|---|
| 기존 경로 | 409,121 | 32.544 | 0.87407 | 기준 |
| 원래 JPEG 그대로 재저장 | 408,076 | 32.544 | 0.87407 | 렌더 완전 동일; 저장 도구만으로 1,045 B 감소 |
| 직접 70% | 342,491 | 32.418 | 0.86467 | 작지만 품질 손실 |
| 직접 76% | 383,877 | 32.588 | 0.87011 | 작지만 지표가 엇갈림; 동등 화질로 채택하지 않음 |
| 직접 80% | 426,476 | 32.715 | 0.87417 | 원본에 더 가깝지만 용량 증가 |
| 직접 90% | 616,040 | 33.062 | 0.88448 | 개선과 용량 증가 |

직접 76%의 JPEG는 375,887 B, 기존 PDF JPEG는 400,086 B다. 이미지 자체 절감은 6.05%이고, PDF 파일 감소 6.17%에는 저장 도구의 1,045 B도 포함된다. 직접 76%의 평균 RGB 변화는 채널별 −0.036/+0.083/+0.031(0~255)이지만 이것만으로 색·디테일 보존을 증명하지 않았다.

**동일 픽셀 밀도는 동일 화질을 보장하지 않는다.** 큰 폭의 일반적 용량 개선을 입증한 실험이 아니다.

## 4. Figma 안의 실행 시간

직접 교체와 저장을 실제 플러그인 iframe에서 실행했다. 같은 후보의 Node 결과와 JPEG·알파·ICC·콘텐츠가 일치했고, 대표 76/80% PDF 렌더도 전부 같았다.

| 구간 | 단일 실행 |
|---|---:|
| Figma 이미지 생성 | 8 ms |
| 기존 방식 대기 | 700 ms |
| Figma PDF 내보내기 | 96 ms |
| 위 세 구간 합 | 804 ms |
| 직접 PDF 검증·교체·저장 | 후보당 25.6~29.9 ms |

두 경로 모두 원본 디코드·JPEG 인코딩은 이 표에서 제외했다(별도 첫 실행 약 93~110 ms/후보). 최초 기준 PDF 생성, 대상 연결, 문서 전체 병합, 폰트 작업, 큰 문서의 메모리 비용도 포함하지 않았다. 따라서 이 표를 31쪽의 총시간 절감으로 환산하면 안 된다. 각 후보를 파일에 기록해 실제 용량을 알 수 있는 것은 확인했다.

iframe의 `crypto.subtle`이 없어서 첫 시도는 실패했다. 최종 내부 경로는 바이트 스냅샷과 직접 비교하며, SHA-256 기록은 외부 분석 도구가 담당한다. 실패 캡처도 별도로 보관했다.

## 5. 픽셀을 바꾸지 않는 JPEG 저장 구조 개선

`jpegtran -copy all -progressive`로 DCT 계수를 유지하면서 저장 구조를 바꿨다. 별도 `-optimize`만 적용했을 때는 이미 Huffman 최적화돼 있어 크기가 그대로였다. [libjpeg-turbo 공식 사용 설명](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/doc/usage.txt)의 `jpegtran` 동작에 근거하며, 실제 픽셀도 별도로 대조했다.

- 사진 한 장: 기존 PDF JPEG 400,086 → 379,801 B(−5.07%), 디코딩 픽셀 동일.
- 31쪽 `v-main.pdf`: **9,778,721 → 9,587,356 B(−191,365 B, −1.957%)**.
- JPEG 66개 중 57개만 더 작아 채택했다. 나머지는 그대로 두었다.
- 재저장 대조군도 9,778,721 B로 같아, 이 경우 감소분은 JPEG 재구성에서 나왔다.
- JPEG 66개 디코딩 픽셀·마스크·ICC 동일. 페이지 31개 콘텐츠·텍스트·MediaBox 동일. 72dpi 렌더 31쪽 모두 화소 차이 0.
- 네이티브 도구 기준 PDF 읽기·대조 저장·66개 처리·최종 저장 약 **918 ms**, 한 번 측정.

이 경로는 픽셀을 바꾸지 않으므로 사진뿐 아니라 Figma가 효과를 래스터화한 JPEG도 같은 방식으로 검토할 수 있다. 다만 현재 도구는 개발용 CLI이고, 플러그인에는 네이티브 실행 기능이 없다. **WASM 실행시간·메모리·패키지 크기·PDF 뷰어 호환성은 아직 검증하지 않았다.** Poppler와 Pillow 결과만으로 모든 뷰어를 보장하지 않는다.

## 6. 코드와 다음 작업

- `tools/pdf-direct-probe/`: 독립 개발 플러그인, 바인딩 분석, 직접 교체, 무손실 실험, 검증 도구.
- `tests/pdfDirectProbe.test.ts`: 직접 교체의 보존·잘못된 입력 거절 9개. 전체 62파일 694통과, 644건너뜀. 타입·린트·제품 빌드 통과.
- 중단 전 제품에 들어갔던 "가장 큰 원본 자동 추가 다운로드" 코드는 백업 후 제거했다. 제품 `src`는 이 브랜치 HEAD와 같다. 제품 빌드를 다시 만들었다. 커밋·푸시·릴리즈 없음.
- 캡처와 PDF는 git에서 제외된 `samples/pdf-direct-20260912/`에 보관한다. 원본 사진은 저장소에 커밋하지 않는다.

다음 우선순위는 **progressive 무손실 변환의 WASM 소규모 시험**이다. 이득이 없는 이미지는 그대로 두고, 실제 Figma iframe에서 메모리·시간과 뷰어 호환성을 확인한다. 전체 문서의 원본→PDF 연결은 별도 큰 작업이며, 이번 한 장의 식별 성공으로 완료된 것으로 취급하지 않는다. 두 경로를 함께 진행하더라도 결과 바이트 검증과 원래 PDF 복구 경로가 필요하다.

작업 중 실행 단축키가 예상과 다르게 동작해 테스트 사진 카드가 벡터로 바뀌었다. 즉시 실행 취소했고, 원래 노드 ID `3759:88763`, 컴포넌트 종류, 두 자식, 위치 29775/−600, 420×300 크기가 복원된 것을 확인했다. 이후에는 메뉴로만 실행했다. 실험 종료 시 선택은 사진 카드였으며 임시 프레임은 남기지 않았다.
